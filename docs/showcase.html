Intent and contract

  • Q1 Intent — written down? Durable work items beside the code.
  • Q2 Proposal — reviewable? A change set with line-level review.
  • Q3 Evidence — deterministic? Checks bound to that change set.
  • Q4 Policy — allowed? Branch rules as reviewable configuration.
  • Q5 Accountability — who merged it? Named code-owner review.
  • Q6 Release — how does it ship? Approval and federated identity.
  • Q7 Feedback — what did production say? Back to stage one.

Nothing migrates for this demonstration. Assess one repository, and compare which of these seven primitives are native, integrated, or custom in your current stack.

Most stacks have several of these primitives natively and bridge the rest. That is a legitimate position, and this session does not ask you to abandon it. Go down the seven and mark each primitive native in your current stack, integrated through a connector you did not write, or custom, meaning a system your own team maintains. The question is only how much of the bridge you are maintaining, and whether an agent can read across it.

Your repositories may be on Bitbucket and your planning in Jira. One repository is enough to test this loop, and migration is not required today.

Note

An agent reads the repository. Intent that lives outside the repository has to be copied into it, and a copy is where accuracy is lost. That is the whole reason this argument is about where evidence lives rather than about which vendor wins.

There are nine lifecycle stages: signal, intent, contract, lane, implementation, evidence, authority, release, production. That is what the loop is made of.

There are eleven demo scenes across fifteen slides. That is how one hour presents the loop. The counts differ because some stages need two scenes and some scenes cover no stage at all.

.github/workflows/repository-pulse.md — the control contract, in review

permissions:  { contents: read, issues: read }   # the agent job can write nothing
timeout-minutes: 10    max-turns: 12    max-ai-credits: 300   # bounded cost
safe-outputs:
  threat-detection: true                          # inspects the proposal
  create-issue: { title-prefix: "[pulse] ", labels: [showcase, pulse, needs-triage], max: 1 }

Six lines of frontmatter decide what this agent may do: what it can read, how long it may run, how many turns it may take, how much it may spend, and the exact shape of the single thing it may write. That is a code review, not a console setting, and it is in the pull request like anything else.

gh aw compile turns it into the committed .lock.yml. Validation recompiles with the pinned compiler and byte-compares against the committed lock, so a source change that was not recompiled fails the build, and so does a hand-edited lock.

Rule

If you cannot read an agent's limits in a diff, you do not have limits. You have hopes.

The pulse lane reads a file that went through a pull request. It is reviewed repository content, and treating it as attacker-controlled would be theatre. What bounds that lane is the control contract above.

The intake lane reads an issue body. Anyone can open an issue, so that text is attacker-controlled, and a model cannot reliably distinguish instructions in its prompt from instructions in the data it was asked to read. That lane needs an input gate, and it has one.

Five boundaries carry the load between them. Only the first is specific to the untrusted-input lane:

  1. Triggering actor and label gate

    Intake only activates on a specific label, compiled into a job-level if: that short-circuits before any model runs. The pulse lane does not need this, and does not have it.

  2. Read-only GitHub permissions

    Both agent jobs hold contents: read and issues: read.

  3. Engine credentials excluded from the supported-lane sandbox

    The compiled lock passes --exclude-env for five named credentials, so the model's environment does not carry them.

  4. Threat detection

    It runs between the agent job and any write, inspecting the proposal rather than trusting the prompt.

  5. A separate, allowlisted safe-output job

    It can only perform what the frontmatter declared.

Rule

Do not ask a model to refuse a malicious instruction. Arrange the system so that obeying one achieves nothing.

The specification, the tests, the checks, the reviewer and the ruleset are identical in all four. That is what makes the choice reversible, and reversible is the only kind of choice worth making this year.

These are two different things and they are easy to conflate. The OpenCode CLI is a local command-line agent: it reads AGENTS.md and the repository from your working tree, and it is unaffected by anything GitHub decides. The OpenCode gh-aw engine was an integration that let that CLI run as the engine of an agentic workflow inside Actions, and it is that integration which ADR-50145 removed.

The positive case for the hosted surface is narrower than a slogan and worth stating plainly:

  • It starts from an issue, so durable intent is the input rather than a chat transcript nobody kept.
  • It needs no developer machine, so work can start when the issue is triaged rather than when someone is free at a laptop.
  • Its session, commits and pull request are attributable in the repository, so the trail survives the person.
  • It is subject to the same rulesets and CODEOWNERS as anyone else, because it proposes through a pull request.

Verdict

That is a reason to try one surface, not a reason to standardise on it. Nothing in this repository depends on it, which is exactly what makes trying it cheap.

The agent may write the plan. It may not apply it.

A GitHub environment holds required reviewers and the deployment configuration. The job requests a short-lived OIDC token and exchanges it with the cloud provider; no long-lived cloud credential is stored in the repository. Keep the trust relationship in a file that goes through review, not in a console setting nobody diffs.

In the Kubernetes case the cluster's admission policy can reject anything the pipeline did not produce, which closes the last gap between approved and running.

Warning

A simulated provenance record proves nothing about the artefact. npm run verify -- --only provenance prints the mode so it cannot be described as verified by accident.

Any operational agent, on any cloud, can correlate production signal with the source that produced it and act under an identity scoped to one workload. That is the pattern. What follows is one implementation of it that actually ran.

  • It correlates live telemetry with connected GitHub source and names the configuration difference between the failing revision and the known-good one.
  • A write-capable rollback subagent shifts all traffic back and drains the faulty revision to zero.
  • Its identity is scoped to that single application, plus a custom role granting only alert read and alert state change.
  • The cloud Activity Log attributes the write to the agent identity, so it is visibly not a human action, and recovery is verified rather than assumed.

Warning

This demonstration proves source grounding and scoped remediation. It does not prove GitHub write-back: the rollback subagent is instructed to raise an issue for source fixes, but its configured tool list contains no GitHub connector, so that is a designed next step and not a demonstrated capability.

A small storefront runs on Azure Container Apps with Application Insights, Log Analytics and Azure Monitor connected. A staged incident ships a revision with a payment-gateway configuration regression and gives it all the traffic; checkout starts returning HTTP 500. The rollback shifts 100% of traffic to the known-good revision under an identity holding Container Apps Contributor scoped to that one app.

Its configured tool list is RunAzCliReadCommands, RunAzCliWriteCommands, QueryAppInsightsUsingAppId, and SearchMemory. There is no GitHub connector in it.

The decision: extend to a second repository, or stop. Not which agent to standardise on — that stays reversible.

  1. GitHub Actions minutes

    Every workflow run consumes them. Public repositories run free on standard runners; private repositories draw on the plan's included minutes and then bill by the minute. Boundable, because the pilot is one repository.

  2. Copilot AI credits

    The Copilot-powered agentic workflows consume AI credits, which is why every workflow here declares max-ai-credits. Boundable, because the ceiling is in the file rather than in an invoice.

  3. GitHub Advanced Security licensing

    On public repositories, code scanning, secret scanning and dependency review are available without an Advanced Security licence. On private repositories they fall under Advanced Security, where code security and secret protection are licensed separately. Confirm the current terms for your plan with your account team rather than quoting a number from a slide.

The pilot runs for two weeks on one repository. We supply this repository, the workflow definitions, and a walkthrough. You supply the repository, the telemetry, and the three people. By day 14 there are five artefacts on the table, and each one is either there or it is not.

  1. An agent-raised issue from your own telemetry

    Not ours. If the workflow cannot find a signal in your data, that is a finding worth having on day 3.

  2. A specification with acceptance criteria mapped to tests

    Checked in both directions, so a criterion without a test fails the build.

  3. A pull request small enough to read in a meeting

    From whichever execution surface the team chose. The surface is not the point.

  4. A check run that blocked something

    A green wall proves nothing. One red check that stopped a merge proves the gate is real.

  5. An attributed approval on a commit SHA

    A named person, a code-owner requirement, a timestamp.

The decision it exists to make is narrow and answerable: extend the loop to a second repository, or stop. It is deliberately not a decision about which agent to standardise on, because that one stays reversible for as long as the contract lives in the repository.

The pilot has two phases, which are periods of time: observation, then enforcement. Beyond the pilot, each repository gets a disposition, which is a decision about that repository and has nothing to do with the calendar.

  1. Migrate

    Active development with existing tests. The loop is worth most where evidence already exists.

  2. Mirror

    Something others depend on, mid-assessment. Pick which side is writable and say so out loud.

  3. Leave in place

    Archived or genuinely inactive. Not everything needs to move.

Assess pipeline definitions before moving anything: gh actions-importer audits Bitbucket Pipelines and other systems and translates most of the mechanical shape. The security posture is the part worth rewriting by hand rather than importing. The path is cloud-neutral: nothing here requires a particular hosting provider.

  1. Write down the contract

    Put AGENTS.md and one specification in one repository. Nothing else changes.

  2. Make the existing evidence count

    Turn on the deterministic checks that already exist and make them required.

  3. Give approval a meaning

    Add CODEOWNERS so an approval means something.

  4. Let one agent propose

    Add one read-only agentic workflow with safe outputs. Watch what it writes for two weeks.

  5. Then, and only then, pick a lane

    Only then decide which execution lane the team prefers. That decision is now reversible.
