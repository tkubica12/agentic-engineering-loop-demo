Intent and contract

An agent writes a plausible diff in ninety seconds. Steering it is nine concerns, and only Implementation is coding. Take the other eight and mark each one native, integrated, or custom in the stack you already run. The maintained bridges behind the custom ones are the platform cost, and nothing on this slide asks you to move a repository to find that number.

SignalWhat changed or deserves attention?
IntentWhy should we act?
ContractWhat must remain true?
LaneWho or what should act?
ImplementationWhat changed?
EvidenceDoes it work and remain secure?
AuthorityWho accepts the risk?
ReleaseWhat is allowed to ship?
ProductionWhat happened after release?

Each question needs a primitive, and the primitive is the thing your platform either has or bridges to: scheduled, bounded automation that reads committed evidence and proposes work; durable, assignable work items an agent can read where the code lives; a specification, a decision record and acceptance criteria stored beside the code; interchangeable execution surfaces bound by one repository contract; a reviewable change set with line-level discussion; deterministic checks and security scanning bound to that change set; required review by named owners, attributed to a person on a commit; environment approval, federated credentials, build provenance; and a path for production signal to re-enter the graph as work.

Note

None of the nine is a model problem. That is the whole argument, and it is why the choice of agent stays reversible for as long as the answers live in the repository.

Most stacks have several of these primitives natively and bridge the rest. That is a legitimate position, and this session does not ask you to abandon it. Go down the nine and mark each primitive native in your current stack, integrated through a connector you did not write, or custom, meaning a system your own team maintains. The question is only how much of the bridge you are maintaining, and whether an agent can read across it.

Existing source control and work management can stay where they are while you find out. One repository is enough to test this graph, and nothing has to move for the answer to be real.

Note

An agent reads the repository. Intent that lives outside the repository has to be copied into it, and a copy is where accuracy is lost. That is the whole reason this argument is about where evidence lives rather than about which vendor wins.

There are nine concerns: signal, intent, contract, lane, implementation, evidence, authority, release, production. That is what the graph is made of. Nothing says work must start at signal.

  • Telemetry enters at Signal. A scheduled workflow reads committed telemetry and finds a rate that moved. This hour enters here, because it is the entry most rooms have never automated.
  • Business intent enters at Intent. Somebody opens an issue because the business wants an outcome. Nothing had to change first.
  • A security finding enters at Evidence. A scanner raises an alert about code that already merged, and the graph runs backwards from there.
  • A production incident enters at Production. A release misbehaves, and the observation is the first thing anyone writes down.

The edges run backwards too, and plurally. Evidence may send work back to the contract or to the implementation, because a failing check either found a defect in the change or a defect in what was asked for. Authority may send it back to intent or to the contract, because a reviewer who declines is rarely rejecting the code. Production may raise a new signal, reshape intent, change what must remain true, or open a proposal directly.

There are eleven demo scenes across fifteen slides. That is how one hour presents the graph, and it walks one readable path through it. The counts differ because some concerns need two scenes and some scenes cover no concern at all. fixtures/prepared/manifest.json holds both numbers, and a test fails the build if any document drifts from them.

Four ways in: telemetry at Signal, business intent at Intent, a security finding at Evidence, a production incident at Production. Any of them can be first, and this demonstration enters at telemetry.

Rule

If you cannot read an agent's limits in a diff, you do not have limits; you have hopes.

Six lines of frontmatter decide what this agent may do: what it can read, how long it may run, how many turns it may take, how much it may spend, and the exact shape of the single thing it may write. That is a code review, not a console setting, and it is in the pull request like anything else.

gh aw compile turns it into the committed .lock.yml. Validation recompiles with the pinned compiler and byte-compares against the committed lock, so a source change that was not recompiled fails the build, and so does a hand-edited lock.

The pulse lane reads a file that went through a pull request. It is reviewed repository content, and treating it as attacker-controlled would be theatre. What bounds that lane is the control contract on the signal slide.

The intake lane reads an issue body. Anyone can open an issue, so that text is attacker-controlled, and a model cannot reliably distinguish instructions in its prompt from instructions in the data it was asked to read. That lane needs an input gate, and it has one.

Five boundaries carry the load between them. Only the first is specific to the untrusted-input lane:

  1. Triggering actor and label gate

    Intake only activates on a specific label, compiled into a job-level if: that short-circuits before any model runs. The pulse lane does not need this, and does not have it.

  2. Read-only GitHub permissions

    Both agent jobs hold contents: read and issues: read.

  3. Engine credentials excluded from the supported-lane sandbox

    The compiled lock passes --exclude-env for five named credentials, so the model's environment does not carry them.

  4. Threat detection

    It runs between the agent job and any write, inspecting the proposal rather than trusting the prompt.

  5. A separate, allowlisted safe-output job

    It can only perform what the frontmatter declared.

Rule

Do not ask a model to refuse a malicious instruction. Arrange the system so that obeying one achieves nothing.

  1. How many alternatives are offered?

    One, or a ranked list? The answer changes the response shape and every test that guards it.

  2. What makes two items interchangeable?

    And is that a clinical or a commercial decision? Nobody in engineering owns that answer.

  3. Must an alternative cover the whole quantity?

    Or is a partial match useful? This one silently decides half the ranking logic.

  4. What happens when nothing in the group is in stock?

    The empty case is the case that reaches production first.

  5. Does the alternative have to be at the same site?

    A constraint that is cheap to state now and expensive to retrofit later.

An agent that answered these itself would have invented the product. Naming them and stopping is the correct behaviour, and it is what turns a signal into intent somebody can accept or reject.

An issue on its own is not the contract. It carries why, and nothing an agent can be judged against. The specification, the mapping, and the decision record. This repository writes those three artefacts by hand to stay dependency-light; the discipline, not the tool, is the point.

Spec-driven development means the specification, not the prompt, is the durable artefact: intent is written down, constraints and acceptance criteria are made explicit, and the agent implements against them rather than against a conversation. Spec Kit is GitHub's own toolkit for that workflow, and it is the reason this scene is a chain rather than a single file.

Its role in the graph is precise and worth stating as a limit rather than a slogan. Spec Kit makes the edge from Intent to Contract durable and repeatable. It does not discover intent for you, so the Signal concern still needs something that watches; and it does not close the production feedback edge, so the Production concern still needs an operational path back into the repository. A spec-driven repository with no signal source and no feedback edge is a well-documented open loop.

The vocabulary around agent loops moved fast in 2026, and three names now come up in most serious conversations. They are named here because attendees will meet them, with the same honesty applied to everything else in this session: each is a community or emerging pattern, none is a GitHub or Microsoft product, and none is a standard anyone has ratified.

  1. Loop engineering

    Replace repeated human prompting with a designed loop: something schedules or triggers the work, state is persisted outside the chat window, output is verified, and the loop escalates to a person or stops. It is the discipline behind the Signal concern, and behind every max-turns and stop condition in this repository. IBM defines it as "the practice of designing agentic workflows, or loops, that iteratively guide AI agents toward completing user-defined goals with minimal human intervention", published 17 July 2026.

  2. The intent loop

    Observation continuously reshapes intent and the specification, rather than intent being captured once at the start. Expressed publicly as a four-step team operating model, "Notice, Spec, Execute, Observe", in a small community repository. In this graph it is the Production feedback edge taken seriously: the specification is expected to change because production said something.

  3. The gauntlet loop

    A maker builds, a separate critic with fresh context judges the artefact against a bar written down before the work started, the largest gap goes back, and the loop repeats until the work clears the bar. Named by Matt Shumer in July 2026 and widely re-implemented since. It improves what arrives at the Implementation concern; it does not replace a deterministic check, because a critic is still a model.

  4. Spec-driven development

    The contract layer, and the oldest idea of the four. It is what the other three iterate around, and the only one of the four with first-party GitHub tooling.

The useful test for any of them is the same one this session applies everywhere: does the pattern leave a durable artefact in the repository that a deterministic check can be bound to? Loop engineering and spec-driven development do. The other two are ways of producing a better proposal, which is valuable and is not evidence.

Source

All read 2026-08-24, all labelled community or emerging. Intent loop: theparlor/intent and its documentation — a small community project, cited for its articulation rather than its adoption. The specification, the tests, the checks, the reviewer and the ruleset are identical in all four. That is what makes the choice reversible, and reversible is the only kind of choice worth making this year.

These are two different things and they are easy to conflate. The OpenCode CLI is a local command-line agent: it reads AGENTS.md and the repository from your working tree, and it is unaffected by anything GitHub decides. The OpenCode gh-aw engine was an integration that let that CLI run as the engine of an agentic workflow inside Actions, and it is that integration which ADR-50145 removed.

The positive case for the hosted surface is narrower than a slogan and worth stating plainly:

  • It starts from an issue, so durable intent is the input rather than a chat transcript nobody kept.
  • It needs no developer machine, so work can start when the issue is triaged rather than when someone is free at a laptop.
  • Its session, commits and pull request are attributable in the repository, so the trail survives the person.
  • It is subject to the same rulesets and CODEOWNERS as anyone else, because it proposes through a pull request.

Verdict

That is a reason to try one surface, not a reason to standardise on it. Nothing in this repository depends on it, which is exactly what makes trying it cheap.

Any operational agent, on any cloud, can correlate production signal with the source that produced it and act under an identity scoped to one workload. That is the pattern. What follows is one implementation of it that actually ran.

  • It correlates live telemetry with connected GitHub source and names the configuration difference between the failing revision and the known-good one.
  • A write-capable rollback subagent shifts all traffic back and drains the faulty revision to zero.
  • Its identity is scoped to that single application, plus a custom role granting only alert read and alert state change.
  • The cloud Activity Log attributes the write to the agent identity, so it is visibly not a human action, and recovery is verified rather than assumed.

What production then does to the graph is plural, and this is the point of the scene: it may raise a new signal, reshape intent, change what must remain true, or open a proposal directly. None of those is "go back to the start".

Five artefacts by day 14: an agent-raised issue from your telemetry, a specification with mapped tests, a pull request small enough to read, a check run that blocked something, an attributed approval. The pilot measures one thing you cannot read off a price list: what it costs your team to keep the bridges behind your custom primitives working. The decision: extend to a second repository, or stop.

  1. GitHub Actions minutes

    Every workflow run consumes them. Public repositories run free on standard runners; private repositories draw on the plan's included minutes and then bill by the minute. Boundable, because the pilot is one repository.

  2. Copilot AI credits

    The Copilot-powered agentic workflows consume AI credits, which is why every workflow here declares max-ai-credits. Boundable, because the ceiling is in the file rather than in an invoice.

  3. GitHub Advanced Security licensing

    On public repositories, code scanning, secret scanning and dependency review are available without an Advanced Security licence. On private repositories they fall under Advanced Security, where code security and secret protection are licensed separately. Confirm the current terms for your plan with your account team rather than quoting a number from a slide.

The pilot runs for two weeks on one repository. We supply this repository, the workflow definitions, and a walkthrough. You supply the repository, the telemetry, and the three people. By day 14 there are five artefacts on the table, and each one is either there or it is not.

  1. An agent-raised issue from your own telemetry

    Not ours. If the workflow cannot find a signal in your data, that is a finding worth having on day 3.

  2. A specification with acceptance criteria mapped to tests

    Checked in both directions, so a criterion without a test fails the build.

  3. A pull request small enough to read in a meeting

    From whichever execution surface the team chose. The surface is not the point.

  4. A check run that blocked something

    A green wall proves nothing. One red check that stopped a merge proves the gate is real.

  5. An attributed approval on a commit SHA

    A named person, a code-owner requirement, a timestamp.

The decision it exists to make is narrow and answerable: extend the graph to a second repository, or stop. It is deliberately not a decision about which agent to standardise on, because that one stays reversible for as long as the contract lives in the repository.

The pilot has two phases, which are periods of time: observation, then enforcement. Beyond the pilot, each repository gets a disposition, which is a decision about that repository and has nothing to do with the calendar.

  1. Migrate

    Active development with existing tests. The loop is worth most where evidence already exists.

  2. Mirror

    Something others depend on, mid-assessment. Pick which side is writable and say so out loud.

  3. Leave in place

    Archived or genuinely inactive. Not everything needs to move.
