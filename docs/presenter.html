Preparation

LiveRuns on GitHub in front of the room. It can fail, so it always has a stop condition.
PreparedRan before the session. Say so once; do not pretend it is happening now.
StaticArticle content. It cannot fail and needs no fallback beyond the page itself.

Rule

Never describe a prepared artefact or a simulated record as something happening live. One discovered overstatement costs the whole hour's credibility.

from a clean checkout

npm run setup
npm run preflight
npm test
npm run verify
npm run aw:install
npm run validate:aw
npm run rehearse

Then walk the slides with the console open. Open the showcase in the browser you will present from, press F12 for DevTools and select the Console tab before entering slides mode, then switch to slides and step to the end with End. The console must stay empty. Any slide-a11y or html-docs warning is a no-go: fix the content, do not present over it.

to rehearse the enterprise profile as well

# PowerShell
$env:SHOWCASE_PROFILE = "enterprise"
npm run preflight
if ($LASTEXITCODE -eq 0) { npm run verify }

# bash, zsh, or any POSIX shell
SHOWCASE_PROFILE=enterprise npm run preflight && SHOWCASE_PROFILE=enterprise npm run verify

An unknown profile name fails immediately with one line and exit code 2, so a typo cannot silently fall back to the sandbox profile. The PowerShell form checks the exit code between the two commands: ; would have run verify even after preflight failed, which is the opposite of what a preflight is for.

  • setup creates the output directories and clears the previous transcript. It installs nothing.
  • preflight checks Node, the documents, the fixtures, and the optional tooling, then prints the capability state for the active profile.
  • test runs the service tests and the repository tests.
  • verify recomputes the telemetry signal and fails if the prepared issue disagrees with the data. It also replays the closing window: npm run verify -- --only followup derives the 32 / 25 / 7 from the real requests and the shipped selection logic.
  • aw:install installs gh aw at the version the committed locks record, removing a different one first if it finds it. It is idempotent and never installs the latest release.
  • validate:aw runs gh aw validate --strict and checks that every lock file was compiled rather than written. It first asserts that this checkout is the git working-tree root, so the freshness comparison cannot pass by recompiling a different repository's workflows.
  • rehearse walks all eleven scenes and fails if any one lacks an artefact, a fallback, an expected state, or a stop condition.

seeding: dry run first, then apply. Replace the placeholder with a repository you own.

npm run seed:remote -- --repo OWNER/REPO
npm run seed:remote -- --repo OWNER/REPO --apply

No default target, by design; --apply is required before anything is written. Seeding creates the labels and the signal issue only, and starts no agentic workflow.

Warning

Be honest about the gap. Seeding installs no workflow: the pulse on tab 2 runs only where .github/workflows/ already lives, which means a fork or copy of this repository that you own, with Actions enabled and Copilot AI credits and policy available to it. Seeding also does not create the pull request on tab 5, the checks on tab 6, or the release run on tab 7, and no script here does. Until you have verified each one, treat tabs 2, 3, 5, 6 and 7 as optional, present those scenes from the prepared artefacts, and say so once.

Rung four of the fallback ladder is a complete presentation on its own: an unseeded session is smaller, not failed.

  1. Run preflight once more

    npm run preflight. If it fails now, present entirely from the prepared path and say so at the start.

  2. Start the local server

    npm run serve. Leave it running. The offline fallback needs it.

  3. Open the eight tabs in order

    Listed in the next chapter. Do not reorder them during the session.

  4. Set the theme and font size

    Dark or light, chosen once. Browser zoom at 100%; the slides fit themselves.

  5. Silence everything

    Notifications off. Second screen shows this guide, not a chat client.

Go 1npm run preflight exits zero.
Go 2The showcase opens in slides mode with a clean console.
Go 3The offline fallback loads and its first scene renders.
Go 4Tabs 2, 3, 5, 6 and 7 are open and readable — which requires a fork or copy you own, with Actions and Copilot credits, and a run that has already happened there.

Conditions 1 to 3 are hard. If any fails, do not present. Condition 4 failing costs the live path only: the pulse then runs as prepared evidence like every other scene, and rung four of the ladder is still a complete hour.

If GitHub or the network is unavailable, open with: "Two segments would normally run live. They ran this morning instead, and I will show you the output and the workflow that produced it." Then never mention it again.

Note

Slides 1, 7 and 10 are the three section dividers. Slide 1 is the cover and carries the title, the subtitle and the thesis; slides 7 and 10 need no tab and no talk track beyond naming the section. Every one of the nine stages is demonstrated by one of the other eight.

Run of show

Say: "An agent can write a plausible diff in ninety seconds. That stopped being the hard part. The hard part is seven questions, and not one of them is a model problem. Was the intent written down? Is the proposal reviewable? Is the evidence deterministic? Is the change allowed? Who is accountable for the merge? How does it reach production? And what did production say back? Mark each one native, integrated, or custom in whatever you run today. Over the next hour a single change answers all seven. Count the stages. One of them is coding."

Expected: The thesis slide: the nine-stage loop, and the seven questions with the primitive each one needs.

Stop: If the deck will not enter slides mode, present the article view and continue.

Do: Open Tab 3 and show the finished [pulse] issue immediately. The room sees the outcome inside fifteen seconds. Only then trigger a fresh run from Tab 2, leave it running in the background, and turn to the source.

Say: "That issue was written by a workflow that read three weeks of committed telemetry — a file that went through a pull request, so it is reviewed repository content, not something an attacker controls. Now look at why you would trust the workflow itself. Six lines of frontmatter decide everything: what it can read, how long it may run, how many turns it may take, how much it may spend, and the exact shape of the one thing it may write. That is a code review, not a console setting. The job that runs the model holds read-only permissions, and the compiled lock excludes five named engine and MCP credentials from the model's sandbox. A separate job with a narrower grant creates exactly one issue with a fixed prefix and three allowed labels."

Then, on product state: "To be exact about what this is: GitHub Agentic Workflows is in public preview, and this repository pins the compiler at gh-aw v0.86.2. What it produces is an ordinary Actions workflow file, committed and reviewable like any other. There is no separate runtime to trust."

If the fresh run finishes before minute 8: put it beside the prepared issue and say "same bounded shape, different run." That is the whole payoff. If it has not finished, say nothing about it and move on — never draw attention to a queue.

Expected: One issue, [pulse] prefix, labels showcase, pulse, needs-triage.

Stop: Show the finished issue first, always. Never make the room watch a queue.

Say: "This one is deliberately not Copilot. Same brief, imported from the same file; one line differs, and that line is the engine. Note what changed here: an issue body is text anyone can write, so this lane gates on a specific label before any model runs. The pulse lane reads reviewed repository content and needs no such gate."

Then, briefly: "The engine died, in fact. GitHub accepted a decision on the fourth of August to remove OpenCode as a supported experimental engine; it still ships as an unsupported sample. Meanwhile the ecosystem grew: Claude and Codex are documented third-party coding agents in public preview. Engines churn in both directions. The brief, the labels, the checks and the reviewer did not move. I run this prepared rather than live, because its compiled lock reports the egress firewall disabled and maps the Copilot token into the model sandbox as an OpenAI key."

Expected: Prepared output: one comment with four headings, at most three allowlisted labels.

Stop: Three minutes, hard. Prepared only: the OpenCode lock reports the firewall disabled and maps the Copilot token into the model sandbox. Never run this lane live.

Say: "An issue becomes a contract when it carries three things: one outcome, the constraints that must stay true, and acceptance criteria somebody could test without asking me. Ten criteria here. Each maps to exactly one named test, and the build fails if a criterion has no test. That mapping is the difference between a specification and a wish."

Then: Thirty seconds on spec-kit. What it is, that this repository writes the same artefacts by hand, and that the value is every repository putting the contract in the same place.

Expected: The specification beside the acceptance mapping.

Say: "Four surfaces, and they are categories, not a vendor count. The IDE — Cursor, VS Code. The command line — the OpenCode CLI, Copilot CLI, Claude Code. A purpose-built agent app. And GitHub-hosted cloud agents, which today means Copilot plus Claude and Codex in public preview. If your team likes Cursor, keep Cursor. Every one of them reads the same specification, is judged by the same tests, and lands in the same pull request under the same rules. That is what makes the choice reversible, and reversible is the only kind of choice worth making this year."

Then, briefly: "One clarification, because it trips people up: the OpenCode CLI is a local command-line agent and nothing GitHub decided affects it. The thing that was removed was the separate integration that let it drive an agentic workflow inside Actions. And the honest case for the hosted lane is narrow: it starts from an issue rather than a chat nobody kept, it needs no developer machine, and its session, commits and pull request are attributable in the repository under the same rulesets as anyone else. That is a reason to try one surface, not to standardise on it."

Expected: The four-tile comparison.

Watch for: This is where a Cursor-preferring audience decides whether you are selling or explaining. Do not open a Copilot window in this segment.

Say: "This delegation ran this morning, because it takes minutes and would spend two later segments. What it received was the issue, the specification, and the repository rules. What it did not receive was any secret, write access to the default branch, permission to add a dependency, or permission to touch a workflow file. Five files, two hundred lines, no dependency change. Small enough to read in this room, which is the actual test of whether the contract was right."

Expected: The Files changed tab, scrolled to the new test file.

Stop: Never start a fresh delegation live.

The longest segment, carried by one slide. The screen changes because you move between GitHub tabs; the deck stays put.

  1. 27 to 31 — Deterministic checks

    Do: Tab 6, the Checks tab. On screen: eight green checks.

    Say: "Eight checks, eight different questions, no model in any of them. Tests on Linux and Windows. Acceptance coverage. Every action pinned to a commit SHA, no pull_request_target, credentials not persisted. And a check that recompiles the agentic workflows and fails if a lock was hand-edited."

  2. 31 to 34 — AI review is a reviewer

    Do: Scroll to the Copilot review comment. On screen: the comment, checks still visible above it.

    Say: "It found the line that would have leaked the internal block. It cannot mark a check green and it cannot satisfy the code-owner requirement. If a probabilistic signal can close a gate, the gate is decorative."

  3. 34 to 37 — The remediation

    Do: Tab 5, Files changed, cursor on the toPublicItem line. On screen: that diff hunk.

    Say: "Spreading the catalogue item straight into the response would have carried four internal fields out. Routing it through toPublicItem makes AC-4 prove the boundary." Then name push protection, dependency review and CodeQL as three controls at three moments.

  4. 37 to 40 — Authority

    Do: Scroll to the merge box. On screen: required review, code-owner requirement, merge button state.

    Say: "Every automated actor here is read-only. One human writes to the default branch, and the approval carries a name and a commit. Autonomy and accountability are not in tension. They are in sequence."

Stop: If a check is still running after three minutes, switch to the prepared evidence artefact.

Do first: Look at the mode field in the provenance record. If it says simulated, say so in the first sentence.

Say: "Provenance answers where an artefact came from without anyone having to trust the answer. Merging is a code decision; deploying is an authority decision, and an environment keeps them separable. The deployment job asks for a short-lived token rather than holding a stored cloud credential. Terraform and Kubernetes are the same shape: the agent may write the plan, it may not apply it."

Stop: Attestation needs an entitled repository. If unavailable, show the simulated record and say so out loud.

Say: "The pattern first, because it is cloud-neutral: any operational agent, on any cloud, can correlate production signal with the source that produced it and act under an identity scoped to one workload. What follows is one implementation that actually ran, on Azure, in a separate public repository. It proves the agent correlated live telemetry with connected GitHub source and named the configuration difference. It proves a write-capable subagent shifted all traffic back to the known-good revision, under an identity scoped to one container app."

Then, mid-scene, without being asked: "What it does not prove is writing back to GitHub. The subagent's instructions tell it to raise an issue for source fixes, but its configured tool list has no GitHub connector. So that is a designed next step, not a demonstrated capability."

Then finish on the bridge: "It also proves the Activity Log attributed that write to the agent and not to a person, and that recovery was verified rather than assumed. That is the shape that matters: production evidence, attributable, under a scoped identity, flowing back to the place the change came from. Whatever runs your production, that is the loop closing — and it is why the next five minutes are about what it costs to try."

Do not raise MDASH here. It is reader depth in the article. Mention it only if someone asks.

Stop: Never open a live cloud portal. This scene is cited evidence from a public repository.

Say: "Nothing here says replace Jira. Work management and engineering evidence are different systems of record. Jira keeps the planning and the reporting the business already reads. Bitbucket repositories stay exactly where they are — nothing migrates during the pilot. What moves closer to the code is the evidence an agent works from."

Then, the cost, before anyone has to ask: "Three lines. Actions minutes, which the pilot bounds because it is one repository. Copilot AI credits for the Copilot-powered workflows, which every file here caps with max-ai-credits, so the ceiling is in the diff rather than the invoice. And Advanced Security licensing, which is what governs code scanning, secret scanning and dependency review on private repositories — public repositories get those without it. Confirm the current terms for your plan with your account team; I am not quoting a number from a slide."

Then, the ask: "One repository, two weeks. Week one is observation only: AGENTS.md, one specification, one read-only workflow, nothing merges differently. Week two makes your existing checks required and adds CODEOWNERS and a ruleset. Three people, part time: the repository owner, a security reviewer, a platform engineer. We supply this repository, the workflow definitions and a walkthrough. By day 14 you have five artefacts — an agent-raised issue from your telemetry, a specification with mapped tests, a pull request small enough to read, a check run that blocked something, and an attributed approval. The decision on day 14 is whether to extend to a second repository. Not which agent to standardise on; that stays reversible."

If asked about migration: Phases are time; dispositions are per repository. After the pilot each repository gets one of migrate, mirror, or leave in place, decided on evidence. gh actions-importer audits Bitbucket Pipelines and translates most of the mechanical shape; rewrite the security posture by hand. The path is cloud-neutral.

Do not: disparage anyone's current tooling. The argument is about which primitives are native, integrated, or custom in their stack — they answer that themselves.

Rule

Say prepared replay, out loud, before you say the numbers. The thirty-two requests are the real ones from the opening telemetry; what the shelf held afterwards is declared synthetic, and the answer is computed from both by the shipped selection logic. It is not a second production run, and no second window was observed. npm run verify -- --only followup recomputes it in front of anyone who asks.

Say: "This is a prepared replay: the same unmet requests, run through the code that shipped. Thirty-two unmet requests, twenty-five now answered with an alternative, seven still not — because by then nothing in the group was left on the shelf. Stage nine became stage one. Nine lifecycle stages, shown in eleven scenes. One of the nine was coding. The other eight are what made the coding safe to keep. All seven questions I opened with now have an answer that does not depend on which model wrote the code. Pick whichever agent you like, and change your mind next quarter. What must not churn is the place where intent, evidence, and authority live."

Then, the one-line ask: "One repository, two weeks, three people, five artefacts, and a decision on day 14."

Then: Stop. Take questions after this, not inside the hour.

Expected: The close slide: follow-up counts, the seven answers, the ask. Then slide 15, the takeaway.

Stop: None. Never cut the close.

The fallback ladder

  1. Rung 1 — Retry once, only if it is instant

    A page that did not load gets one reload. A workflow that failed does not get a second run.

  2. Rung 2 — Switch lane

    Only in the intake scene: the supported Copilot lane replaces the experimental one and produces the same shape.

  3. Rung 3 — Prepared artefact

    Open the prepared output for the scene from Tab 8. Say "this is the output from this morning's run" once, then carry on.

  4. Rung 4 — Offline fallback

    mission-control.html. Every scene, click or keyboard, no network. Every simulated state is labelled on screen.

Warning

Descending the ladder mid-scene is normal and costs nothing. Climbing back up mid-scene to retry a live path is what turns a small failure into a visible one.

A cut is only available before the scene runs. Look at the clock at each checkpoint, and take cuts from that checkpoint's list only.

  1. Checkpoint 1 — minute 10 entering intake, and again at minute 13

    Recoverable here: 5 minutes. If you are over at minute 10, cut intake to one sentence — state the swappability claim and skip the prepared comment body — which saves 3 minutes. At minute 13, if still over, skip spec-kit entirely in the contract scene for another 2 minutes; it is context, not argument.

  2. Checkpoint 2 — minute 27 entering evidence, and again at minute 29

    Recoverable here: 11 minutes. In order: name the eight checks from the slide rather than opening the Checks tab (3 minutes); show the provenance record and skip the OIDC and Terraform detail (2 minutes); keep the four proven production claims and the one limitation but drop the architecture walk (3 minutes); keep the pilot shape, the three cost lines and the five artefacts but drop the disposition detail (3 minutes).

Rule

Do not try to recover time from a scene that has already run, and never cut the close or the commercial ask. Finish at minute 60 with the seven questions answered and the pilot named, then take questions. Question time is after the hour, not inside it; say so at minute 0 so nobody interrupts to save you.

The article carries far more than the fifteen slides. That extra material sits inside reveals and inside cards that are deliberately not slides, and it is written for someone reading afterwards at their own pace.

In slides mode the runtime leaves reveals closed by design. Do not open one on stage: the text is sized for reading, not for the back of a room, and every reveal you open is a minute you did not budget.

Rule

If a point matters to the talk, it is already on the slide. If it is behind a reveal, it is an answer to a question you have not been asked yet. Send the article afterwards.

Afterwards

after the session

npm run reset

node scripts/cleanup.mjs --repo OWNER/REPO
node scripts/cleanup.mjs --repo OWNER/REPO --confirm
  • reset clears generated output and rebuilds the standalone export from its source. It does not delete it, and it never discards your working tree.
  • cleanup without --confirm lists what it would act on and changes nothing.
  • cleanup only touches items carrying the demo marker and the uniquely prefixed labels the seed created. Anything else is listed and left alone, even with --confirm.
  • There is no default target repository. Omitting --repo is an error, by design.

between two sessions

npm run reset
npm run setup
npm run preflight

To seed a fresh repository for the live path, use the dry run first. It creates nothing until you pass --apply, and everything it creates carries the demo marker.

seeding a target repository

node scripts/seed-remote.mjs --repo OWNER/REPO
node scripts/seed-remote.mjs --repo OWNER/REPO --apply

Every live path in this hour has a prepared answer, and the rehearsal command fails if one of them does not.
